# TRNG Project Guide

This guide explains the project as it currently exists: its directory layout, how the RTL modules work together, what each file does, and how to run the simulation. The design follows the plan in [PLAN.md](PLAN.md).

## Project Directory

```text
trng-fpga/
├── Makefile
├── PLAN.md
├── PROJECT_GUIDE.md
├── Project Report - Phase 1.pdf
├── README.md
├── build/                         # Generated by make test / make wave
│   ├── random_bits.txt            # Corrected bits, one 0/1 character per bit
│   ├── tb_ring_osc                # Compiled oscillator testbench
│   ├── tb_trng_top                # Compiled full-project testbench
│   └── trng.vcd                   # Waveform opened by GTKWave
├── src/                           # Synthesizable design modules
│   ├── ring_osc.v
│   ├── synchronizer.v
│   ├── trng_top.v
│   └── von_neumann.v
├── tb/                            # Simulation testbenches
│   ├── tb_ring_osc.v
│   └── tb_trng_top.v
└── tools/
    └── analyze_entropy.py
```

The `build/` files are generated output, not source. `make clean` removes that directory; the next simulation recreates it.

## How Data Flows

```text
Three ring oscillators
        │ asynchronous outputs
        ▼
Three two-stage synchronizers, sampled by i_clk
        │ synchronized values
        ▼
XOR of the three synchronized values
        │ raw sample, each enabled system-clock cycle
        ▼
Von Neumann pair corrector
        │ o_random_bit with o_valid
        ├──► captured and printed by the top-level testbench
        └──► accumulated into a 128-bit demonstration key
                     │
                     ▼
          XOR editable plaintext with key bytes
                     │
          hexadecimal ciphertext, then XOR again
                     ▼
                decoded text
```

The top-level RTL uses three oscillators with default inverter counts 3, 5, and 7. Each oscillator output is sampled through its own two-register synchronizer. The synchronized values are XORed to form one raw bit. The Von Neumann corrector consumes raw bits in pairs: `01` produces `0`, `10` produces `1`, and `00` or `11` produces no output. Therefore the corrected stream has a variable rate.

## Source Files

### RTL: `src/`

- **`ring_osc.v`**: Parameterized ring oscillator. When compiled for synthesis with `SYNTHESIS` defined, it builds an enabled inverter loop and applies `keep`/`dont_touch` attributes. In behavioral simulation, it instead toggles a register using delayed events and randomized timing. `SIM_HALF_PERIOD` defaults to `N + 2` time units and `SIM_JITTER` defaults to 2 time units.
- **`synchronizer.v`**: Two clocked registers that sample an asynchronous oscillator output into the system-clock domain. The first register may still become metastable in hardware; the second stage gives it time to settle but does not guarantee that metastability is impossible.
- **`von_neumann.v`**: Stores the first bit of a pair, compares it with the next valid bit, and emits a corrected bit and one-cycle `o_valid` pulse for unequal pairs. It discards equal pairs and clears a partial pair when `i_valid` is low.
- **`trng_top.v`**: Connects the three oscillators, their synchronizers, the XOR operation, and the corrector. `i_reset_n` is active-low; `i_enable` enables the oscillators and the corrector input stream.

### Testbenches: `tb/`

- **`tb_ring_osc.v`**: Enables one simulated oscillator, counts transitions, then checks that it oscillated.
- **`tb_trng_top.v`**: Generates a 10 ns system-clock period, releases reset, enables the design, and waits for 128 valid corrected bits. It prints each bit and writes the same stream to `build/random_bits.txt`. It also writes `build/trng.vcd` for GTKWave.

  The testbench contains the editable `plaintext` string. It limits the plaintext to 16 bytes because 128 bits provide 16 key bytes. After capture, it prints the key and ciphertext in hexadecimal, XORs the ciphertext with the same key bytes, checks the decoded bytes against the original text, and prints the decoded text. The default text is currently `Hello harsha`; edit the `plaintext` declaration to change it.

### Analysis: `tools/`

- **`analyze_entropy.py`**: Reads a text file containing `0` and `1` characters and reports the bit count, zero/one counts, proportion of ones, run count, autocorrelation at a selected lag, and empirical Shannon entropy. These are basic descriptive measurements, not formal NIST SP 800-22 or AIS-31 certification.

### Root Files

- **`Makefile`**: Defines the compile, simulation, waveform, analysis, and cleanup commands. `IVERILOG`, `VVP`, and `GTKWAVE` can be overridden on the make command line.
- **`PLAN.md`**: The implementation and verification plan for the project.
- **`README.md`**: Short setup and usage notes.
- **`Project Report - Phase 1.pdf`**: Project report document included in the workspace.

## Running the Project

Install Icarus Verilog (`iverilog` and `vvp`) and GTKWave, then run these commands from the project directory:

```sh
make test
```

This compiles and runs both testbenches, captures 128 bits, prints the encoded/decoded demonstration, and analyzes the captured bitstream.

```sh
make wave
```

This runs the full top-level simulation and opens `build/trng.vcd` in GTKWave. GTKWave is a waveform viewer; `vvp` performs the simulation.

```sh
make clean
```

This removes generated files under `build/`.

## Important Limitations

- The simulated oscillator timing uses simulator pseudo-random delay variation. It is a behavioral stimulus for checking the surrounding logic; it does not reproduce physical FPGA noise or prove that the resulting bits have real entropy.
- The XOR encryption is included to demonstrate encoding and decoding. It is not secure as run here: the simulation source is not a validated random source, and the testbench prints the key. Never use this generated key for protecting real data.
- XOR encryption only has one-time-pad security when the key is truly random, secret, as long as the message, and never reused. Here the captured 128-bit key allows messages up to 16 bytes in the testbench, but the other security conditions are not met.
- Simulation success checks functional behavior only. Hardware use requires a target FPGA, device-specific synthesis/implementation, and validation of the actual entropy source.
